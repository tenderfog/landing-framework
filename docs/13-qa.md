# QA: Web, iframe та реальні застосунки

QA доводить конкретну поведінку конкретної збірки. Screenshot не доводить нарахування, зелений тест не доводить WKWebView, а handshake не доводить рендер модалки.

Нові regression families беруться з [каталогу багів і popup cleanup](22-incidents-and-popup-cleanup.md), [promo patterns](21-promo-patterns.md) і [widget workflow](19-surfaces-and-workflows.md). Для косметичної правки виконати affected checks, не весь каталог. Після cleanup перевіряється clean release variant без diagnostic listeners: instrumentation може змінити intermittent touch behavior.

Для кожної кампанії створіть дві окремі задачі: [QA Web](../templates/qa-web.md) і [QA App](../templates/qa-app.md). Поточна App-задача може мати blockers і бути оновлена після native fix; не приховуйте їх спільним статусом «все працює».

Для нових лендінгів обов’язкові **Vue 3 + Nuxt 4**. До runtime QA перевірити manifest/lockfile, typecheck/generate, actual output на campaign subpath і включення framework chunks у performance measurements. Окремі regression cases: hydration mismatch, user data у generated HTML/payload, спалах available CTA до auth/mission readiness, дубль bridge/listeners після remount і media/WebGL cleanup. [Технічний стандарт](00-technical-stack.md).

## 1. Рівні доказу

| Рівень | Що підтверджує | Чого не підтверджує |
| --- | --- | --- |
| Static / unit / VM | Парсер, стани, дедлайни, guards, checksum, template compile | Реальну auth, CORS, Journey delivery, native GPU |
| Local standalone | Layout, assets, interaction, fallback | Реальний host routing, token contract, fullscreen parent popup |
| Local host harness | Схему, token timing, origin rejection, height grow/shrink | Роботу реального продуктового SDK/сокета |
| Product Stage Web | Реальні account/profile/missions, product event actions, browser integration | Паритет Swift/RN Android |
| Actual iOS WKWebView | Нативну сесію, renderer, socket, lifecycle, GPU конкретного пристрою | Android та інші версії App/ОС |
| Actual RN Android WebView | Android WebView/native adapter/lifecycle конкретного build | iOS |
| Production smoke | Опублікований exact build, live route/cache/основний journey | Повну заміну Stage QA |

У звіті використовуйте `PASS`, `FAIL`, `BLOCKED`, `NOT_TESTED`, а також поле `evidence_level`. «Теоретично має працювати» не є `PASS`.

## 2. Підготовка даних

Зафіксуйте version/commit, Stage host і landing URL, Figma nodes/стани, версію approved copy, locale, QA-період, timezone та точну конфігурацію місії/Journey/бонусів. Campaign dates і QA dates зберігайте окремо.

Для тестів потрібні fixture aliases, які можна знайти в захищеному сховищі:

- `guest`;
- `auth_unverified`;
- `auth_verified_available`;
- `auth_verified_consumed`;
- за потреби — completed/claimed/locked/expired/empty missions.

Не публікуйте credentials, token або raw profile response в задачах і скриншотах. Account mapping для відтворення доступний лише уповноваженому QA у захищеному місці. Для винагород і результатів використовуйте спеціальні тестові бонуси та погоджений QA label.

## 3. Основна матриця станів

Конкретні labels і правила беріть із [state matrix](04-state-and-time.md), а не переносіть текст минулої акції.

| Сценарій | Очікувана властивість |
| --- | --- |
| Гість | Participation CTA відкриває auth/registration modal через погоджений event action; opt-in не викликається |
| Auth=true, token ще не прийшов | Loading без спалаху активних participation controls |
| Profile/missions loading | Controls лишаються у визначеному pending state |
| Неверифікований | CTA для верифікації та participation controls ведуть у verification; не запускають місію |
| Verified + спроба доступна | Approved available style, tooltip/focus/hover; кнопка активує потрібну місію |
| Клік / double-click / alternate control click | Один request; загальний guard для всіх кнопок, не окремий guard на кожну |
| Затримка результату | Візуальний loader має скінченний budget; невизначеність не дозволяє повторної видачі |
| Consumed / cooldown | Controls присутні або приховані саме за дизайном; якщо видимі — disabled, без доступної анімації; countdown не дублює business logic |
| SDK/profile/schema/network error | Людське повідомлення, fail-closed для участі, контрольований retry |
| Logout / account switch | Стан попереднього користувача очищено; late responses ігноруються |
| Кампанія ще не почалась / завершилась | Approved state і CTA; не видає нову participation attempt |

Якщо verification перевіряється лише UI, backend eligibility все одно належить продукту/Smartico. QA має окремо підтвердити серверні обмеження відповідно до scope кампанії. Disabled DOM-кнопка не є захистом винагороди.

## 4. Сесія, токени та конкурентні відповіді

Обов'язкові негативні тести:

1. Відправити token пізніше першого render; controls не вмикаються за query `auth=true`.
2. Передати invalid/null/expired token; invalid не перетворюється на «verified», а null застосовує guest state за контрактом.
3. Змінити token того самого користувача під час pending request; не отримати повторний opt-in через reset UI guard.
4. Перемкнути account A → B, поки profile/mission A затриманий; відповідь A не змінює B.
5. Logout під час API-запиту; abort і generation check працюють, навіть якщо abort не зупинив відповідь.
6. Повторно відкрити screen або init компонент; не подвоюються SDK, handlers, observers і RAF.
7. Перевірити відмову origin whitelist, SDK load error, timeout, empty missions, invalid response schema.

VM-тести з fake tokens годяться для race/guard, але fake token не підтверджує реальну авторизацію чи server verification.

## 5. Час, reset і дати

Для календарної акції з reset `00:00 Europe/Kyiv` перевірте:

| Ситуація | Що має бути доведено |
| --- | --- |
| Використана спроба вдень | Countdown до наступної локальної півночі, не `clickedAt + 24h` |
| Верхній і нижній countdown | Один deadline і tick, однаковий час |
| Reload після півночі зі stale consumed response | Не вигадує нові 23 години; refresh і стан очікування серверного reset |
| Timer дорівнює нулю | Сам по собі не відкриває opt-in; право повертає валідна оновлена місія |
| Вкладка / App були у фоні | Одразу перерахувати час і перечитати стан при foreground |
| Зміна timezone пристрою | Кампанія лишається у `Europe/Kyiv` |
| День переходу DST | Календарний день може бути 23 або 25 годин; відлік правильний |
| Backend reset заданий у UTC | Встановлений час відповідає Києву для всього campaign period; зміна DST врахована |
| Закінчення «включно» | End boundary є наступний день `00:00` у timezone кампанії, а не її останній день `00:00` |

Перевірка лише client countdown не доводить recurrence backend. Для реального reset потрібні Stage evidence до/після boundary та server state. QA clock override у unit/harness — окремий тест, не production time manipulation.

## 6. Smartico: окремо місія, Journey та модалка

Перевіряйте ланцюг [за runbook](05-smartico-missions-journeys.md): identity → read missions → opt-in/Client Action → Journey trigger → branch → popup → claim/navigation → серверний результат. Кожний крок має свій owner.

- Обидва participation choices, якщо так задумано, запускають **одну** місію, а не дві незалежні добові спроби.
- Mission opt-in не викликається повторно через другу кнопку, reload або profile recheck.
- Server caps/idempotency підтверджені окремо від client guard.
- Попап відповідає конкретній branch і має approved copy/іконку/кнопки.
- Якщо close дорівнює claim — перевірте обидва шляхи та одноразову видачу. Це правило не переноситься на кожну майбутню акцію автоматично.
- Risk/continue не виконує claim іншої branch.
- Lost/result CTA відкриває правильний bonus/game/product screen, а не довільний web URL у Safari.
- Детерміновані test fixtures/branch configuration кращі за багато випадкових кліків. Кілька результатів не доводять статистичне 50/50.
- Тестовий бонус може мати іншу фактичну конфігурацію, ніж production reward: QA фіксує це явно.

Для fullscreen popup перевіряйте **actual ancestor container**: `100vw` усередині обмеженого iframe не робить popup full-page. Потрібна підтримка parent/native presentation. Деталі — [popup templates](06-smartico-popup-templates.md).

## 7. Перевірка шаблону реальним engine

Не обмежуйтеся відкриттям експортованого статичного HTML. Візьміть фактичний template body з Smartico, чинний `tmpl` engine і конфігурацію, яку отримує popup. Зафіксуйте URL/version/checksum engine та template body, щоб test result можна було відтворити після оновлення платформи.

```text
матриця перевірки
 = усі content states
 × button visibility combinations
 × desktop/mobile dimensions
 × supported locales
```

Для кожного комбо: compile без exception → root непорожній → видимий контент → правильні labels/actions → external assets завантажені. Якщо у перевіреної реалізації було 24 комбінації, не копіюйте число як стандарт: генеруйте повну матрицю із параметрів нового template.

Типографіку, наприклад `font-size:16px; line-height:24px`, перевіряйте за актуальним design token. Це не універсальне значення для будь-якого тексту.

Перевіряйте literal template delimiter collisions після фінальної minification. CSS `width:100%}` може зламати engine, який сприймає `%}` як закриття template directive. Реальні directives мають лишитися; literal `%}` потрібно розірвати, наприклад `width:100%; }`. Не виконувати global replace по всьому template навмання.

Для Web/App окремо перевірте CSP, font CORS, HTTPS asset URLs, root selector і load/render exception. `PAGE_READY`, `READY_TO_BE_SHOWN` чи impression є доказом відповідного handshake кроку, а не візуального рендеру.

## 8. Навігація та product parity

Звірте **кожну** action row з [реєстром event actions](03-event-actions.md): auth modal, verification, game modal, category, bonuses, approved PDF/rules.

Для Web перевірте звичайний click, keyboard activation, fallback href/modified click, Back і правильний parent destination. Для App — handler → native screen → повернення, без відкриття непотрібного браузера.

Smartico `dp:ok` / `dp:cancel` — бізнес-команди popup, а `dp:go&url=.../event_action/...` — навігація. Не замінюйте всі Smartico кнопки навігаційним action: це змінить Journey semantics.

Ненаданий PDF не замінюється технічним описом чи правилами іншої акції. CTA має погоджений disabled/hidden state до затвердженого URL і handler.

## 9. Layout, доступність і локалізація

Покриття визначає actual audience matrix. Як smoke використовуйте 320/375/430/768/1440 і широкий desktop; доповніть реальними найчастішими viewport, iOS Safari та Android Chrome. Desktop resize не замінює actual WebView.

- `scrollWidth <= clientWidth` у landing document та host.
- Повна ширина декору/каруселі не обмежена content container.
- Parent overlays, bottom nav, safe areas й landscape не блокують CTA/sound.
- FAQ grow **і shrink**, асинхронний font/image relayout та orientation коректно змінюють iframe height.
- Root height не залежить від viewport shell `100vh`, який може залишити порожній простір або resize loop.
- Keyboard focus/Enter/Space, `aria-expanded`, labels, disabled state і tooltip доступні; touch не залежить від hover.
- Довгі переклади, fallback locale, шрифтова кирилиця, countdown format та locale switch протестовані.
- У публічному тексті немає службових SDK/vendor/debug labels, токенів і raw error codes.
- Декоративний raster title не розтягнутий понад роздільність джерела/DPR; media variants обираються за реальним CSS size.

Порівнюйте дизайн та реалізацію в однакових viewport/state; зберігайте конкретні відмінності, а не лише «схоже». Деталі — [Figma/assets](08-figma-and-assets.md), [responsive UI](09-responsive-ui.md), [локалізація](16-localization.md).

## 10. Відео, карусель, анімації та WebGL

| Перевірка | Очікування |
| --- | --- |
| Cold і warm video cache | Poster до готового кадру; не лишається поверх відео, що вже грає |
| Autoplay blocked / media error | Poster і доступний manual start, без порожнього hero |
| Sound toggle | Actual muted/play state, accessible label, user gesture; без unmuted autoplay обіцянок |
| Offscreen/hidden/background | Дорогі loops, video і character зупинені |
| Reduced motion | Nonessential рух вимкнений, статичний корисний контент лишається |
| Карусель | Циклічність без стрибків; hover/focus/touch pause; swipe; focus не потрапляє у недоступні clones |
| Lazy game covers | Завантажуються near-view cards, не вся бібліотека й не всі копії одразу |
| WebGL unavailable / context throw | Робочий fallback, controls не залежать від canvas |
| Shader compile / link / first draw failure | Fallback лишається видимим; renderer не оголошено ready завчасно |
| Context lost | Animation stop, коректний fallback/recovery policy |
| SVG/filter/image failure | Останній CSS/static fallback, читабельний текст |
| Native GPU compositing | Правильний чорний/brand background, немає opaque smoke rectangles/seams |

Перевірка WebGL повинна запускати реальний render probe, а не тільки `getContext()` truthy. Функціональні mocks ловлять переходи fallback, але device capture потрібен для GPU compositing.

Вимірюйте initial transfer, deferred bytes, long tasks/frame time, активні canvas pixels/FPS і idle/background behavior. Малий JS gzip не доводить малого GPU навантаження. Бюджети — у [performance](11-performance.md), implementation — у [media/motion/WebGL](10-media-animation-webgl.md).

## 11. Аналітика

Поки канал не реалізований — `NOT_TESTED / contract pending`, а не «analytics pass». Коли реалізований: exact emitted names за словником аналітика `ga_*`, довжина GA4 names до 40 символів, один owner `page_view`, exact CTA IDs, consent, delivery, dedupe, error sanitization, no token/PII, no duplicate Smartico reports. Незавершений validation pattern `ga_{screen}_{field}_status_` не підставляється у код без уточнення. `activation_successful` доводиться accepted opt-in ack, а не відкриттям popup; `grant_successful` має серверний owner. Див. [план](12-analytics.md).

## 12. Мінімальний багрепорт і вихід

Багрепорт: build SHA/asset version, surface, browser або App build/OS/device/WebView version, locale, fixture alias, local campaign time + UTC timestamp, preconditions, дії, expected/actual, sanitized console/network/native evidence, screenshot/recording, layer hypothesis. Не додавати password/token.

Завершення QA означає: критичні сценарії пройдені на потрібних surfaces; залишкові ризики й `NOT_TESTED` перелічені; owner і дата підтвердження прив'язані до exact build. Зміна template, recurrence, action routing, assets або bridge після QA потребує affected regression, а не автоматичного перенесення попереднього `PASS`.
